## 0001　工具层用 MCP 协议承载，而不是本地函数

**决策** ✅：把 `query` / `schema` 等能力做成独立的 MCP Server 进程，主程序通过 MCP 客户端调用。

**背景**：项目 1 里工具是本地 `@tool` 函数，只能被同一个 Python 进程使用。

**理由**：
1. 工具与客户端解耦——同一套工具能被 Web UI、Claude Desktop、其他 Agent 复用，不必每个客户端重写一遍
2. 进程隔离——工具层崩溃不影响主程序
3. 可替换——将来换 PostgreSQL，只要换 Server 实现，客户端代码一行不改

**代价**：
- 每次调用多一层进程间通信（stdio），实测单次调用增加约 5-10 ms
- 调试链路变长：报错可能来自客户端配置、进程启动、协议、工具实现四层
- 部署时多一个进程要管

**证据**：`mcp_server/server.py` 与 `scripts/check_mcp.py` 跑通，`['query', 'schema']` 两个工具可被 LangChain Agent 直接使用。

## 0002　模型用 DeepSeek，但保留 Ollama 可切换

**决策** ✅：默认 `deepseek-flash`，通过 OpenAI 兼容协议接入；`llm_provider` 可切回 `ollama`。

**背景**：项目 1 用本地 qwen2.5:7b，经常出现"有 token 无 content 无 tool_call"的空响应（约 1/3 概率）。

**理由**：
- 本项目完全依赖 tool calling（多 Agent 调度、MCP 工具调用），空响应会让整条链路失效
- 实测 `deepseek-flash` 返回 `finish_reason: "tool_calls"`，参数解析正确
- 用 `model_provider="openai"` + 自定义 `base_url`，不必依赖专门的 SDK 包

**代价**：
- **数据出网**：SQL 与查询结果会发往第三方，项目 1 的"数据不出内网"卖点在本项目不成立，README 里不能这么写
- 成本随调用轮数线性增长，多 Agent 场景要额外做预算控制
- 它是推理模型，返回里带 `reasoning_content`，回填 messages 时需注意

**已否决** ❌：直接写死 `model_provider="deepseek"`。需要额外安装 `langchain-deepseek`，而 OpenAI 兼容层已能满足，少一个依赖。

## 0003　只读由数据库强制，不靠字符串过滤

**决策** ✅：连接串使用 SQLite URI `file:...?mode=ro`，任何写操作在数据库层被拒绝。

**背景**：常见的"安全检查"是匹配 SQL 里的 `DROP` / `DELETE` 关键字。

**理由**：字符串黑名单永远有漏——注释、大小写、多语句、`SELECT ... INTO` 都能绕过。只读连接是白名单机制，由数据库执行。

**实现细节**：两层防御，职责不同。
- `run_query` 里的前缀检查（只允许 `SELECT`/`WITH`/`PRAGMA`）→ 目的是**给模型一条能看懂的报错**
- `mode=ro` → 目的是**真正的安全边界**

**代价**：只读连接无法执行 `ATTACH`、临时表写入等操作；某些分析场景（建中间表）会被限制。

**证据**：`scripts/check_db.py` 中执行 `DELETE FROM orders` 返回"只允许 SELECT / WITH / PRAGMA 查询"，未到达数据库即被拦截。

## 0004　强制 LIMIT，并多取一行判断截断

**决策** ✅：SQL 未写 `LIMIT` 时自动补 `LIMIT max_rows + 1`；取回后若行数超过 `max_rows`，截断并标记 `truncated=True`。

**理由**：
- 不加限行，`SELECT * FROM order_items` 会一次拉走 15 万行
- 多取一行是分页的标准做法——只有拿到第 N+1 行，才知道"结果比上限多"
- `truncated` 要透传给模型，它才知道"条件太宽"，从而主动加 `WHERE` 或聚合

**踩过的坑**：第一版补的是 `LIMIT max_rows`，导致 `fetchmany(max_rows + 1)` 永远拿不到第 N+1 行，`truncated` 恒为 `False`。这个错误不报异常，只是让"截断提示"静默失效。

**代价**：`LIMIT` 注入改变用户 SQL 的语义（尤其是带 `ORDER BY` 时，截断的是排序后的前 N 条，可能不是用户想要的子集）。

## 0005　查询超时用 `set_progress_handler` 实现

**决策** ✅：每次执行前设定 deadline，注册 progress handler，每 2000 条虚拟机指令检查一次，超时返回非 0 中止。

**背景**：SQLite 没有 `statement_timeout` 这类参数。

**理由**：笛卡尔积、无索引的全表扫描可能让单次查询跑几分钟，拖死整个 Agent 流程。`set_progress_handler` 是 SQLite 提供的唯一可中断入口。

**代价**：
- 检查有粒度（2000 条指令），极短查询无法精确控制
- 超时后连接状态不确定，实现里直接关闭连接而不复用

## 0006　所有路径配置在 `config.py` 统一解析为绝对路径

**决策** ✅：用 pydantic 的 `field_validator` 把 `db_path` / `chart_dir` / `output_dir` 的相对路径统一拼上 `BASE_DIR`。

**背景**：`.env` 里写 `DB_PATH=data/business.db` 时，pydantic 会直接采用这个相对路径，于是结果取决于**进程的当前工作目录**。实测从 `D:\python_test` 启动时找不到数据库，报"数据库不存在"。

**理由**：服务化之后（uvicorn、Docker、MCP 子进程）工作目录不可控，路径必须与启动位置无关。

**代价**：配置对象依赖模块级常量 `BASE_DIR`，写测试时需要能替换。

**证据**：修复后从任意目录启动，`settings.db_path` 都指向 `...\data_analysis_agent\data\business.db`。

## 0007　`temp_store = MEMORY` 绕开临时文件创建失败

**决策** ✅：连接建立后执行 `PRAGMA temp_store = MEMORY`，并做成配置项 `sql_temp_store`。

**现象**：`GROUP BY` 类查询间歇报 `unable to open database file`，而简单查询和 `ORDER BY` 正常。

**定位过程**（控制变量）：
1. 小查询 `SELECT COUNT(*)` → 正常
2. 大排序 `ORDER BY unit_price DESC` → 正常（能走内存 top-N，不落盘）
3. 大聚合 `GROUP BY product_id` → **失败**
4. 大连接 `orders JOIN order_items GROUP BY o.id` → **失败**
5. `PRAGMA temp_store = MEMORY` 后重跑 → **全部正常**

**根因**：进程解析出的临时目录是相对路径（实测 `tempfile.gettempdir()` 返回项目目录而非系统 Temp），SQLite 建临时 B 树文件失败。`GROUP BY` 必须落盘，`ORDER BY ... LIMIT` 可以在内存完成，所以只有前者暴露问题。

**代价**：临时表放内存，大表（GB 级）排序会吃光 RAM。因此做成配置项，部署到大表环境可切回 `FILE`。

## 0008　MCP 子进程启动时显式指定 `cwd`

**决策** ✅：`MultiServerMCPClient` 的 stdio 配置里显式传 `"cwd": str(ROOT)`。

**现象**：`Error while finding module specification for 'mcp_server.server' (No module named 'mcp_server')`，客户端表现为 `Connection closed`。

**理由**：stdio 传输是**客户端拉起子进程**，子进程 cwd 继承自客户端。IDE 的运行配置里工作目录不一定是项目根，`python -m 包.模块` 就会找不到包。

**双层防护**（各自解决不同问题）：
- 客户端传 `cwd` → 保证 `-m mcp_server.server` 能找到包
- server.py 顶部 `sys.path.insert(项目根)` → 保证 server 内部能 import `data_agent`

**代价**：路径硬编码依赖项目根位置；若将来打包分发，需要用环境变量或 entry point 替代。

## 0009　工具错误分级：SQL 错误让模型自修，环境错误直接中断

**决策** ✅：给 `QueryError` 增加 `kind` 字段，区分 `ErrorKind.SQL` 与 `ErrorKind.ENV`；MCP 工具按类型返回 `[SQL_ERROR]` / `[ENV_ERROR]` 前缀；`ask.py` 在整轮结束后检测到任何 `ENV_ERROR` 就作废答案并退出。

**结果**：同类问题从 8~9 次工具调用降到 5 次；`ENV` 判定依据 SQLite 报错文本（`unable to open database file` / `database is locked` / `disk i/o error` / `out of memory` / `interrupted`）。

**背景**：0007 那个 bug 发生时，Agent 把"数据库打不开"误解为"查询范围太大"，于是把查询拆小重试了 6 次，最后在回答末尾轻描淡写地写"疑似资源限制，不影响结果"。

**理由**：两类错误的正确响应完全不同。
- `no such table` / `no such column` → 模型改 SQL 就能解决，回灌有价值
- `unable to open database file` / 超时 → 改 SQL 无用，继续重试只会掩盖故障

**现状风险**：现在所有异常都变成一句"查询失败"，模型只能靠猜，实测一次问答题触发了 9 次工具调用（其中 4 次是环境错误引起的无效重试）。

**待实现**：`QueryError(kind=...)`、MCP 工具按 kind 返回不同标记、Agent 层遇到 `env_error` 直接终止并提示用户。

## 0010　口径必须由系统定义，不能交给模型

**决策** ✅：在 System Prompt 中写明各指标口径，并把口径固化进评测集的期望 SQL。

**结果**：加入口径段落后，同一问题连续两次运行给出同一个数字（44,462,665.78），且模型主动在答案末尾声明所用口径；改动前同一问题两次运行分别为 44,462,665.78 与 44,493,428.10。

**证据**（同一个问题，两次回答，两个数字）：

| 轮次 | 成交额 | 口径 |
| --- | --- | --- |
| 第一次 | 44,462,665.78 | 商品金额 − 订单折扣（不含运费） |
| 第二次 | 44,493,428.10 | 纯商品金额（不含折扣、不含运费） |

两个数字都能自圆其说，差值 30,762 元正是当月折扣合计。**问题不在模型，在于系统从未定义"成交额"是什么。**

**理由**：企业里口径由数仓或指标体系定义（metrics layer），模型只负责取数。把口径交给模型自由选择，结果不可复现，也无法做回归测试。

**待实现**：口径写进 prompt + 评测集逐题固定期望 SQL + 答案中必须声明所用口径。

## 0011　`schema` 工具需要补充业务语义

**决策** ✅：在 `describe_schema()` 的输出里增加字段的业务含义（`COLUMN_NOTES` 常量，如 `discount` 是订单级减免金额，不是折扣率）。

**结果**：加入语义后，同一问题的工具调用从 8 次降到 5 次，且不再出现"查 discount 取值分布""查 unit_price 范围"这类为猜语义而发的探查查询；`(1 - discount)` 这类误用未再出现。

**证据**：同一个问题，Agent 花了 4 次调用专门探查字段语义——查 `discount` 的取值分布、查 `unit_price` 的取值范围、查月份天数是否完整。

其中一次还写错成 `unit_price * (1 - discount)`，把减免金额当成了折扣率，得出 −2.4 亿的月成交额，随后自行发现并纠正。

**理由**：schema 只有列名和类型，业务含义全靠猜。把语义写进 schema 描述，能同时降低调用次数和误解概率。

**代价**：语义维护成本转移到人工；表结构变更时需要同步更新描述。

## 0013　数据生成固定随机种子

**决策** ✅：`random.seed(42)`，并在生成前删除旧库、重建全部表。

**理由**：评测结果必须可复现。若每次生成的数据不同，"昨天 78%、今天 81%"就无法判断是代码改动还是数据变化。

**代价**：数据完全确定，无法用于测试"分布漂移"这类场景。

**决策** ✅：用姓名字库 + `random` 自行拼接。

**理由**：少一个依赖；当前只需"看起来像人名"的字符串，Faker 的能力过剩。

## 0015　先做单 Agent 基线，暂不拆分多 Agent

**决策** ✅：当前架构是单 Agent + MCP 工具。

**理由**：没有单 Agent 的基线数据，就无法证明多 Agent 拆分带来了什么。拆分的收益（上下文隔离、职责分离）必须用同一套评测集量化，否则只是架构炫技。

**计划**：评测集与基线跑出来后，再拆 Supervisor + SQL Agent + Chart Agent + Reviewer，用同一批题对比准确率、调用次数、延迟、成本，并把结论写入本日志（无论正负）。

**代价**：多 Agent 是职位描述里的高频关键词，晚一步意味着简历上暂时少一个亮点。

## 0017　单 Agent 基线：12 题自动判分 11 通过

**记录** ✅：口径与 schema 语义落地后的第一轮基线。

| 指标 | 数值 |
| --- | --- |
| 自动判分 | 11/12（91.7%） |
| 平均工具调用 | 2.9 次 |
| 环境错误 | 0 |

**唯一失败**：`diamond_aov`（钻石会员平均客单价）。评测期望 10,036.53（商品额 − 折扣，不含运费），模型给出 10,026.40。

**归因**：差额 `(10036.53 − 10026.40) × 2788 ≈ 28,244`，与钻石会员已付款订单的运费合计吻合。模型口径选择是"实收"（减了运费），与 prompt 中"不含运费"不符。**属于口径混淆，不是计算错误。**

**四条开放式题目的表现**（均合格）：
- "哪个商品卖得最好"——主动声明按销量统计，并附带销售额
- "12 月成交额"——回答"数据只覆盖到 2026-10-31，12 月尚未发生"，未编造 0
- "employees 表"——1 次调用即拒绝，并列出实际存在的 4 张表

**推论**：口径混淆是主要错误来源，而不是"不会写 SQL"。后续优化应优先消除口径歧义（例如让模型必须从固定枚举中选择口径并显式输出），而非增加 Agent 数量。

## 0018　错误三分法：SQL / TRANSIENT / FATAL

**决策** ✅：把工具错误从两类细分为三类，并给出不同重试策略。

| 类型 | 判定依据 | 策略 |
| --- | --- | --- |
| SQL | `no such table`、`no such column`、语法错误 | 修正后重试（受 Agent 循环上限约束） |
| TRANSIENT | `interrupted`（超时）、`database is locked`、`unable to open database file` | 简化查询后重试**一次** |
| FATAL | `disk i/o error`、`out of memory`、`database disk image is malformed` | 立即中止，答案作废 |

**为什么从两类改成三类**：0009 最初的实现把超时也归入"环境错误"，策略是"永不重试"。
实测中一次偶发超时（`oct_with_freight`）直接导致整题无法作答，而该题只需换一种写法即可完成。

**代价**：TRANSIENT 允许重试一次，最坏情况下多一次无效调用；FATAL 与 TRANSIENT 的边界依赖错误文本匹配，不同 SQLite 版本的措辞可能不同。

**证据**：细分后同一题连续多轮均通过（5 次调用），评测输出中出现 `⚠偶发` 时仍给出正确答案。

## 0019　评测集自身的缺陷比模型错误更常见

**决策** ✅：评测题目纳入版本管理，并遵守三条规则。

**规则**：
1. **参考 SQL 必须与 `METRIC_DEFINITIONS` 逐条对齐**——口径说"只统计 paid"，参考 SQL 就必须带 `status='paid'`
2. **`id` 全局唯一**——重复 id 会让同一题被跑两次、期望值互相矛盾
3. **判分只看结论段**（答案前 400 字），避免"顺带提到某个数字"被误判为答对

**实证一（参考 SQL 违规）**：`top_product_qty` 的参考 SQL 是
`SELECT MAX(SUM(quantity)) FROM order_items GROUP BY product_id`，未过滤订单状态，期望值 601。
模型回答"已付款口径 538 件"——**模型是对的，评测是错的**。若不发现，优化方向会从"改模型"变成"改一个没坏的东西"。

**实证二（重复 id）**：新增题目时未删除旧行，导致 `top_product_qty` 出现两条、期望值分别为 601 与 538，
同一份代码连跑两次出现 12/12 与 11/12 的波动，误判为"模型不稳定"。

**代价**：题目需要人工维护，新增时要同时核对口径、id、参考 SQL 三件事。

## 0020　判分容差要跟量级走

**决策** ✅：`is_hit` 的容差改为 `max(|期望值| × 0.1%, 0.05)`，即相对误差加绝对下限。

**背景**：`h3_diamond_share` 期望 4.80、模型答 4.81，被判错。两者都是真实值 4.805 的正确舍入。

**理由**：相对 0.1% 对大批量数字合适（4,446 万差 4 万块无所谓），但对小数值过于苛刻（4.8 差 0.01 就出局）。
容差必须与量级匹配，否则评测会把"舍入差异"误判成"计算错误"。

**代价**：绝对下限会让小于 100 的指标容忍 0.05 的误差，极小的百分比差异（如 0.01%）无法被检出。

## 0022　Web 界面推送"执行过程"，而非仅推送 token

**决策** ✅：FastAPI + SSE，`stream_mode="updates"` 逐节点推送工具调用与结果；前端把每次调用渲染成一条时间线。

**理由**：
1. 数据分析 Agent 的价值在"查了什么、算出什么"，推工具调用比推逐字输出信息量大
2. 只处理 `updates` 事件比同时处理 token 与工具调用混流简单，不需要处理分帧边界
3. 用户能看到进度，不必干等十几秒

**踩过的坑**：
- MCP 工具返回的是内容块列表 `[{"type": "text", "text": ...}]`，直接 `str(content)` 会把 Python repr 打到前端。需要按 `type == "text"` 取文本。
- 模型有时用制表符对齐而不是 Markdown 管道表格，前端渲染器需要同时兼容两种，否则表格退化成纯文本。

**代价**：无 token 级逐字效果，长回答的等待感略强；前端需要自己实现 Markdown 子集（标题、粗体、表格、图片）。

## 0023　类目级指标的口径未定义，由模型自行选择并声明

**观察** ⚠️：查询"笔记本类目累计消费超过 5 万元的客户数"时，折扣是订单级字段，而订单可跨类目。
模型自行选择了"按金额比例分摊折扣到笔记本部分"，并在答案中明确声明该口径未在 schema 中定义，
随后做了稳定性验证：

| 折扣处理方式 | 结果 |
| --- | --- |
| 按金额比例分摊（选中方案） | 2,622 人 |
| 折扣全部计入笔记本 | 2,622 人 |
| 完全不扣折扣 | 2,625 人 |

**评价**：这个行为是好的——主动声明假设、并证明结论对假设不敏感。但它属于**模型的自发行为，
不是系统保证**：换一个模型或换一次提问，可能换成别的分摊方式而不声明。

**待改进**：类目级指标的折扣分摊规则应写入 `METRIC_DEFINITIONS`，由系统统一规定，
而不是每次靠模型自选。

**代价**：规则一旦写死，跨类目的边界情况需要人工定义；且会让口径表变长，占用上下文。
